# Native bridge integration

The native application must register two tools backed by the same service
configuration used by Kai's normal chat models:

- `image_models`
- `image_generate`

The implementation belongs in the provider/service abstraction, not inside
the Linux sandbox.

### Credential boundary

The bridge receives a model id and request parameters. It resolves the model
to the configured provider internally and uses the provider's existing
credential store.

The Skill sees only:
- model metadata
- generated file paths
- errors

It never sees:
- API keys
- Authorization headers
- cookies
- encrypted settings

### Model selection

A model should be considered image-capable only when its provider adapter
declares text-to-image or image-to-image support. Kai already has per-model
image capability gating for chat input; the bridge should use the same model
catalog rather than inventing a second catalog.

### Output

Generated bytes should be written into Kai's existing sandbox/file result
pipeline, then returned as file paths. This lets the existing chat renderer
display the generated image without the Skill having to know provider-specific
URLs.
